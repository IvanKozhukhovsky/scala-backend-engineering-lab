A trait is a named capability

The Scala 3 Book treats a trait as the primary shared interface: abstract members are required services, concrete members are provided services.1 You cannot construct a trait on its own.2

Scala 3 Book, OOP Modeling, section Traits. The Showable example there is a classic trait — no type parameter yet.
Tour of Scala: Traits: classes and objects extend traits; traits have no constructor you can call. 
trait Show:
  def show: String
  def showHtml: String = s"<p>$show</p>"

case class Document(text: String) extends Show:
  def show: String = text

Document is a Show. Anywhere a Show is expected, a Document is allowed — that is subtyping. showHtml is already implemented; only show had to be filled in.

That is the right tool when the types are yours and they really share one hierarchy. It is the wrong tool when String, a library Role, and your User must all become a log line — they should not all extends Show.

Methods after the type is closed

Extension methods add a method to a type after it is defined, including types whose source you cannot edit.3

Scala 3 Book, Extension Methods. The Book’s Circle cannot grow a circumference field in its original file. 
case class Circle(x: Double, y: Double, radius: Double)

extension (c: Circle)
  def circumference: Double = c.radius * math.Pi * 2

Circle(0, 0, 5).circumference

The extension (c: Circle) clause is the receiver: inside the method, c is the value on the left of the dot. Several methods can share one extension block. If the method lives in another package, you import it — the compiler will even suggest the import.

An extension is syntax. It does not, by itself, let one function say “this works for every type that can be shown.” That is the next step.

A given instance beside the type

A type class is a parameterized trait whose implementations are given instances, not subclasses.4 You add behaviour to a closed type without making that type extend anything.

Scala 3 Book, Type Classes, and Reference: Implementing Type classes. Same definition: new behaviour, no subtyping.
Classic traitType class
Shape trait Show trait Showable[A]
How a type joins A extends Show a given Showable[A]
Who you can extend Types you own Also types you do not own 
trait Showable[A]:
  extension (a: A) def show: String

case class Person(firstName: String, lastName: String)

given Showable[Person] with
  extension (p: Person) def show: String =
    s"${p.firstName} ${p.lastName}"

Person("John", "Doe").show   // "John Doe"

The Book puts show on Showable as an extension so the call site looks like the classic trait: person.show, not showable.show(person). The capability lives next to Person, so a JSON codec or a log format can live in another file without editing the case class.

An enum from Day 07 is the same move: keep Role as data, supply given Showable[Role], and match every case in that given — not case _. 

enum Role:
  case Admin, Member, Guest

given Showable[Role] with
  extension (r: Role) def show: String =
    r match
      case Role.Admin  => "admin"
      case Role.Member => "member"
      case Role.Guest  => "guest"

using and the compact bound

A function that needs the capability takes it as a context parameter. The compiler fills that argument from a given in scope.5

Scala 3 Book, Context Parameters: a using clause marks the parameter; a given is the canonical value. [A: Showable] is the Book’s compact form of (using Showable[A]). 
def showAll[A](as: List[A])(using Showable[A]): List[String] =
  as.map(_.show)

// same contract, shorter:
def showAll[A: Showable](as: List[A]): List[String] =
  as.map(_.show)

showAll(List(Role.Admin, Role.Guest))   // List("admin", "guest")

If no given Showable[A] is in scope, this does not compile — that is the point. You cannot silently .toString a type that was never shown. Later backend libraries (JSON codecs, equality, pretty-printing) are this pattern with different names. Do not pull those libraries in yet.
