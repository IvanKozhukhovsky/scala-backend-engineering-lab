A package is a namespace

A package names a region of code so two Stock types in different regions do not collide. You declare it at the top of the file. Same-package members see each other without an import.1

Scala 3 Book, Packaging and Imports: packages create namespaces; “Import clauses are not required for accessing members of the same package.” 
package day12.core

case class Item(sku: String, priceCents: Int)

def priceOf(items: List[Item], sku: String): Option[Int] =
  items.find(_.sku == sku).map(_.priceCents)

By convention the folder matches the package: src/main/scala/day12/core/…. Scala does not require that layout; this repo follows it so you can see the boundary in the tree.2

Tour of Scala: Packages and Imports: one convention is package name = directory; Scala itself is agnostic to file layout.

day12.core and day12.shell are siblings. Nested names do not grant a free view of the sibling. Core does not magically see printPrice.

An import is an arrow

To use a name from another package you import it. That line is a compile-time dependency: this file now depends on that package.3

Scala 3 Book, Packaging and Imports: import pkg.Name one member; import pkg.{A, B} a few; import pkg.* the rest (not givens). Stop before renaming, hiding, and import pkg.given — Day 08 already covered givens. 
package day12.shell

import day12.core.{Item, priceOf}

def printPrice(items: List[Item], sku: String): Unit =
  priceOf(items, sku) match
    case Some(cents) => println(s"$cents")
    case None        => println("unknown")

The shell may import the core. That is the only arrow this unit allows. If priceOf imported printPrice, the core would depend on I/O and you could not test the catalog without bringing the shell along.

Shell depends on core

Day 11 already split functions: debit returns a value; printDebit prints. Packages make that split visible in the import graph. A comment can be ignored. An import the core is not allowed to write is a boundary you can review — and the compiler will not resolve a name that was never imported.

Tests of the decision live with the core (same package, or they import only day12.core). They do not import the shell. They do not capture stdout.

If a later function needs the time, keep passing now as data, as in Day 11. If you later name a capability as a trait, declare that trait in the core package and implement it in the shell — still no import the other way. Do not introduce an IO type. Do not split an sbt/mill subproject yet: here a “module” is a package with a one-way import arrow.

Worked example: day12.core and day12.shell. The suite Day12Suite is in package day12.core — it never mentions the shell. Keep the modules cheat sheet open while you code.
