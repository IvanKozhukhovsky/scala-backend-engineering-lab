Function versus socket

Days 17–19 already tested the HTTP contract: method, URI, status, JSON. That is still the fast suite. It never speaks HTTP/1.1. There is no TCP listen, no Host header, no wire Date. Client.fromHttpApp is the same layer with a client-shaped API.1

http4s Client.fromHttpApp: “useful for generating pre-determined responses in testing.” It does not open a socket. Keep it for fakes. This unit’s skill is Ember over loopback.

Ember is http4s’ native backend. Quick Start and Service start it with EmberServerBuilder; the client page starts EmberClientBuilder. Both .build to a Resource — acquire, use, release, including on error or cancel, same as Day 15.2

http4s Client: Client.run itself returns Resource[F, Response[F]] because the connection is finite. Read the body inside use. This repo pins http4s-ember-server and http4s-ember-client 0.23.36. slf4j / logback still wait; NOP log lines in tests are expected.

Ember is a Resource

Bind 127.0.0.1, not 0.0.0.0. Server.baseUri is what the client will call. A URI whose host is 0.0.0.0 is a listen address, not a destination. port"0" asks the OS for a free port so parallel tests do not collide on 8080 — http4s’ own Ember suites do the same. After bind, baseUri holds the real port.3

http4s Service shows withHost(ipv4"0.0.0.0") and withPort(port"8080") for a long-running app (.use(_ => IO.never)). Tests are not that app: loopback plus port 0, then exit. 
import com.comcast.ip4s.{ipv4, port}
import org.http4s.ember.client.EmberClientBuilder
import org.http4s.ember.server.EmberServerBuilder

def serve(app: HttpApp[IO]): Resource[IO, Server] =
  EmberServerBuilder
    .default[IO]
    .withHost(ipv4"127.0.0.1")
    .withPort(port"0")
    .withHttpApp(app)
    .build

def withLive[A](app: HttpApp[IO])(run: (Uri, Client[IO]) => IO[A]): IO[A] =
  Resource
    .both(serve(app), EmberClientBuilder.default[IO].build)
    .use { case (server, client) =>
      run(server.baseUri, client)
    }

Inject DeskConfig("quotes", 1) the way Day 19 injected QuoteConfig. The live test still does not own env. Keep convertAmount / rateOf pure.

expect is for 2xx

client.expect[A] decodes a successful response. A 404 or 422 fails the IO with UnexpectedStatus — it does not hand you ApiError. That is the opposite of HttpApp.run, which always yields a Response.4

http4s Client: expect decodes on success. status / statusFromUri return the code. run(req).use is the seam when you need status and body (a 422 JSON error). Finish reading the body before use exits. 
withLive(app) { (base, client) =>
  client.expect[RateOut](base / "rates" / "EUR")
}

withLive(app) { (base, client) =>
  client.statusFromUri(base / "rates" / "JPY")  // 404
}

withLive(app) { (base, client) =>
  val req = Request[IO](POST, base / "convert").withEntity(ConvertIn("EUR", 0))
  client.run(req).use { res =>
    res.as[ApiError].map(err => (res.status, err))
  }
}

A live GET through Ember typically carries a Date header. HttpApp.run does not add one. That is a cheap check that the request actually left the process.
