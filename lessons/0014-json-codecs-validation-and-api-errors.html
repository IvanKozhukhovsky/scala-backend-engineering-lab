Encoder and Decoder are type classes

JSON is a serialization format at the rim. Inside the service you still want case classes. circe’s Encoder[A] writes A as Json; Decoder[A] reads the other way — the same “given instance beside the type” shape as Day 08.1

http4s JSON Handling recommends circe and shows a hand-written Encoder, then derivation. The page’s circe-generic + paradise plugin is Scala 2. On Scala 3.3 this repo uses derives Codec.AsObject from circe-core (pulled in by http4s-circe). 
import io.circe.Codec

final case class RateOut(code: String, cents: Int)
  derives Codec.AsObject

RateOut("EUR", 108)
// JSON object {"code":"EUR","cents":108}

Codec.AsObject is both encoder and decoder for a JSON object. Field names follow the case class. Keep rateOf a pure Option function — the codec does not look anything up.

jsonOf sits at the HTTP edge

http4s still speaks bytes. An EntityEncoder[F, A] turns A into a body and sets Content-Type: application/json. An EntityDecoder[F, A] parses the other way. jsonEncoderOf / jsonOf are the bridges from a circe codec.2

http4s JSON Handling: jsonOf[F, A] needs a Decoder[A] and yields EntityDecoder[F, A]. Prefer that over CirceEntityCodec._, which would try JSON for every type with a decoder — including in scopes that also serve text. 
import org.http4s.circe.jsonOf
import org.http4s.circe.jsonEncoderOf

given EntityDecoder[IO, ConvertIn] = jsonOf[IO, ConvertIn]
given EntityEncoder[IO, ConvertOut] = jsonEncoderOf[IO, ConvertOut]

Ok(ConvertOut("EUR", 1080))   // 200 + application/json

Day 17 used req.as[String] on the response. For a request body, prefer req.attemptAs[ConvertIn].value: you get Either[DecodeFailure, ConvertIn] — the Either you already match on. req.as[A] fails the IO instead. Without Ember, that failed task is not turned into an HTTP status; it blows up the test.3

http4s Error Handling: if a MessageFailure is not handled by the service, it reaches the backend as a failed task, and the server maps it to a response. This unit still runs HttpApp.run in-process, so you map the Either yourself.

400 syntax, 422 meaning

RFC 9110 splits two client mistakes that look similar in a debugger.4

RFC 9110 §15.5.1: 400 is malformed syntax (or similar). §15.5.21: 422 Unprocessable Content — the content type and syntax are fine, but the instructions cannot be processed. http4s 0.23.31+ names the DSL UnprocessableContent (422); older pages say Unprocessable Entity.
  • MalformedMessageBodyFailure — not JSON. Map to 400 and {"error":"malformed_json"}.
  • InvalidMessageBodyFailure — JSON object, wrong shape (missing field, qty a string). Map to 422 and {"error":"invalid_json"}.
  • Domain Either — qty < 1, unknown code in the body. Still 422, with a different error string.
  • GET on a missing item URI — still 404 not_found, as on Day 17. Wrong method — still 405 + Allow. Do not reuse not_found for those.
req.attemptAs[ConvertIn].value.flatMap {
  case Left(_: MalformedMessageBodyFailure) =>
    BadRequest(ApiError("malformed_json"))
  case Left(_: InvalidMessageBodyFailure) =>
    UnprocessableContent(ApiError("invalid_json"))
  case Right(in) =>
    convertAmount(in.code, in.qty) match
      case Left(ConvertError.InvalidQty) =>
        UnprocessableContent(ApiError("invalid_qty"))
      case Left(ConvertError.UnknownCode) =>
        UnprocessableContent(ApiError("unknown_code"))
      case Right(out) =>
        Ok(out)
}

convertAmount stays pure. HTTP only chooses the status and the error string. This repo pins http4s-circe 0.23.36 next to http4s-dsl. Ember still waits.
