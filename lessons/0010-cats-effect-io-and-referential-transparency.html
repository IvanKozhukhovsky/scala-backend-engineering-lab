A description, not a start

An IO[A] is a computation which, when evaluated, can perform effects before returning an A. Until then it is only a description: a pure, immutable value.1

Cats Effect, IO: “An IO is a data structure that represents just a description of a side effectful computation.” Effects “are not evaluated until the ‘end of the world’” — an unsafe run method, or an IOApp.

Day 13’s Future.apply starts work. IO.apply (written IO { ... } or IO(...)) suspends a by-name body: building the value does not run the body.2 That is the table in the docs: asynchronous eager is Future; asynchronous lazy is IO.

IO, “On Referential Transparency and Lazy Evaluation”: Future[A] is eager; IO[A] is lazy. “Laziness goes hand in hand with referential transparency.” 
def lookupRate(code: String): IO[Option[Int]] =
  IO(rateOf(code))

rateOf is still Day 11’s cake: a function of its argument. lookupRate is a recipe that says “when run, call that function.” No ExecutionContext parameter appears on these signatures — the runtime behind IOApp / unsafeRunSync owns scheduling later.

IO.pure(x) lifts an already-known value. Its argument is evaluated now, by value — so never put println inside IO.pure. Suspension is IO { ... }, not pure.3

IO, “Pure Values”: “IO.pure cannot suspend side effects, because IO.pure is eagerly evaluated… so don’t do this: IO.pure(println("THIS IS WRONG!")).”

Referential transparency

Referential transparency means you can replace an expression with a name bound to the same value and the program still means the same thing. With IO, naming a suspended effect and using that name twice still means “run this description twice.” The docs’ gauge example is the test: factoring addToGauge(32) into a val must not change how many times the gauge updates.4

IO: naming the task and sequencing it twice “doesn’t work with Future, but works with IO.” Effects are not memoized; a single description may be run multiple times.

That is why Day 11’s purity talk and Day 13’s eagerness collide: a backend wants to compose effect descriptions the way it composes Option values, then run once at the rim of the process.

map the value; run only at the edge

map on an IO is the same idea as on Option or Future: transform the successful result inside the description. Nothing runs until the whole program is executed. 

def convert(code: String, amount: Int): IO[Option[Int]] =
  lookupRate(code).map(maybeRate => maybeRate.map(_ * amount))

The application edge is IOApp.Simple: you provide a val run: IO[Unit], and Cats Effect runs it for you.5 Tests and the REPL may call unsafeRunSync() after importing cats.effect.unsafe.implicits.global — useful, named unsafe, not for library cores.6

Getting Started: object HelloWorld extends IOApp.Simple { val run = IO.println("Hello, World!") }
Getting Started, REPL: unsafeRunSync() “is not meant to be used within a normal application… very useful for REPL-based experimentation and sometimes useful for testing.”

Stop here: no fibers, no Resource, no cancellation API, no FS2. Those are later units. Do not reach for Future inside these functions.

Worked example: Day14.scala and Day14Suite.test.scala. The suite proves construction does not run the body, and that sequencing the same IO twice runs it twice. Keep the IO cheat sheet open while you code.
