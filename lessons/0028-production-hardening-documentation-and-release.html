Three names, one SemVer

Semantic Versioning: a version is MAJOR.MINOR.PATCH. Software using SemVer MUST declare a public API — ours is the Day 29 OpenAPI document.1 The FAQ is blunt: v1.2.3 is not a semantic version. Prefixing v is a git-tag convention. Major version zero (0.y.z) is initial development; anything MAY change; the public API SHOULD NOT be considered stable.

SemVer 2.0.0. Start initial development at 0.1.0. Once a versioned package is released, its contents MUST NOT be modified — ship a new version instead. Stop before pre-release identifiers and build metadata as skills.

Humans, not git logs

Keep a Changelog: a changelog is a curated, chronologically ordered list of notable changes for each version. Changelogs are for humans, not machines. Do not dump git logs — merge commits and “fix typo” lines are a step in the source, not a noteworthy difference for a caller.2 Group by type: Added, Changed, Deprecated, Removed, Fixed, Security. Omit empty sections. Dates are ISO 8601 (2026-09-09). Keep an [Unreleased] section at the top.

Keep a Changelog 1.1.0. The file should be CHANGELOG.md. GitHub Releases are a non-portable extra; keep the markdown in the repo. Stop before yanked-release markup as a required skill.

A tag is not a Release

GitHub: releases are deployable software iterations you package with release notes and optional binaries. They are based on Git tags. A tag date may differ from a release date — you can tag today and write notes later.3 Automatically generated notes list merged pull requests. GitHub’s own wizard says: check that they include all and only what you want. That list is a draft, not Keep a Changelog.

About releases and Automatically generated release notes. The pre-release checkbox marks “not ready for production.” This unit builds githubReleaseOf as a string. It does not call the Releases API or create a tag. 
githubReleaseOf(quotesNotes)
// tag:        quotes-v0.1.0
// title:      quotes 0.1.0
// prerelease: true          // 0.y.z
// body:       the 0.1.0 section, not git log

Portfolio Level 3 also wants API examples a stranger could follow. startupOf lists GET /health, a known code, a miss, and one POST — statuses from the OpenAPI document. Building that markdown does not docker run.

0.1.0 is not production

SemVer FAQ: if your software is being used in production, it should probably already be 1.0.0. The contrapositive is the honesty rule: 0.1.0 is initial development. GitHub’s pre-release flag matches. Portfolio readiness is explicit: describe the capstone outcome; do not claim the lesson repository itself is a production service. A sentence that says is a production service, production-ready, deployed to, or hosted at fails overclaimsProduction.
