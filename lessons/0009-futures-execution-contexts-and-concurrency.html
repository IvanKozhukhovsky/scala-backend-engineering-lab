A placeholder, already started

A Future[T] is a placeholder for a T that may not exist yet. When the computation finishes, the future is completed with that value, or failed with the exception the body threw.1

Scala API, Future: “a value which may or may not currently be available, but will be available at some point, or an exception if that value could not be made available.”

You do not start it later. Future.apply starts the body on an execution context and returns the placeholder at once. The work is already in flight while you still hold a Future.2

Scala API, Future.apply: “Starts an asynchronous computation and returns a Future instance with the result of that computation.” The Scala Book says the same: a future “immediately begins running the block of code inside the curly braces.” 
def fetchRate(code: String)(using ExecutionContext): Future[Option[Int]] =
  Future {
    rateOf(code)
  }

rateOf is still Day 11’s cake: a function of its argument. fetchRate is the icing that says “run that lookup off this thread.” Future.successful(x) is the other constructor: already completed, no pool. This unit’s fetches should schedule with Future { }.

Constructing two futures starts both. Combining them afterwards is how overlapping work happens. Creating the second only inside the first’s map would wait. Stop there: you do not need flatMap or a Promise yet.

The ExecutionContext is the pool

An ExecutionContext runs the body — typically on a thread pool, not necessarily on the thread that called Future { }.3 map needs one too: the function runs later, when the value arrives.

Futures and Promises: “you can think of execution contexts as thread pools.” ExecutionContext.global is the built-in pool. Skip custom executors, blocking { }, and “run on the current thread.”

Day 08 already taught the wiring. Methods that need a pool take (using ExecutionContext). Tests and @main import ExecutionContext.Implicits.global at that edge. Do not hide global inside fetchRate — the API’s advice is to choose the context in one place and pass it in.4

Scala API, ExecutionContext: prefer (implicit ec: ExecutionContext) on methods (Scala 3: using) over hardcoding import ExecutionContext.Implicits.global in library code.

map the value; Await only at the edge

map on a future is the same idea as map on Option: transform the successful value; if there is no value, there is nothing to transform. If the original future failed, the mapped future fails with the same exception.5

Futures and Promises, combinators: “You can reason about mapping futures in the same way you reason about mapping collections.” Skip onComplete as a skill — it returns Unit, like foreach: side effects, not a value. 
def fetchConverted(code: String, amount: Int)(using ExecutionContext): Future[Option[Int]] =
  fetchRate(code).map(maybeRate => maybeRate.map(_ * amount))

The test still needs a T, not a Future[T]. Await.result(future, 1.second) blocks the current thread until the value arrives or the timeout fires. The API recommends avoiding that except where you must — a test or a main is that place.6 MUnit can also wait if the test body returns the Future. Either way, do not Await inside fetchConverted.

Scala API, Await: result “will block the calling thread’s execution until they return, which will cause performance degradation, and possibly, deadlock issues.” “While occasionally useful, e.g. for testing, it is recommended that you avoid Await whenever possible — instead favoring combinators.”

This is still not an IO type. A Future is eager: constructing it is doing the work, not describing it. Day 14 exists because that difference matters for a backend. Do not import Cats Effect here.
