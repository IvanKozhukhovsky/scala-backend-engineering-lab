HTTP and REST contracts

You can name a resource with a URI, choose an HTTP method as the operation, and return a status as the outcome — then encode that contract as HttpRoutes[IO] and run a Request through it without binding a port.

Method, URI, status

An HTTP request names what (the target URI) and what to do (the method). The response’s status is how that intention turned out.1

RFC 9110: methods carry request semantics; a resource must not treat a request in a way that contradicts the method. GET/HEAD/OPTIONS/TRACE are safe (read-only). PUT, DELETE, and the safe methods are idempotent (repeat has the same intended effect). POST is neither.
  • GET — transfer a representation. Must not request a state change.
  • PUT — replace the resource; repeating it should land in the same state.
  • POST — process the body according to the resource; not safe, not idempotent.
  • DELETE — remove the resource; idempotent.

Status classes: 2xx success, 4xx the client’s request is the problem, 5xx the server failed. For this unit keep four codes in muscle memory: 200 OK (GET found it), 404 Not Found (no such resource), 405 Method Not Allowed (resource exists, that method does not), 204 No Content (success with an empty body — http4s will not let you put a body on it).

The resource contract

“REST” here means a uniform contract, not “JSON over HTTP.” A URI identifies a resource. The method is the operation. The status is the result. Clients should be able to retry a safe or idempotent call after a network blip without inventing extra protocol.2

A common bug: every unmatched method becomes 404 because the router never considered the URI. RFC 9110: if the method is known but not allowed for that resource, respond 405 and include an Allow header listing the methods that work.

Keep rateOf a pure Option function, same as Days 14–16. HTTP is the shell: it chooses a status from that value. Do not hide the catalog inside Ok { … }.

HttpRoutes is a function

http4s models a service as Request[F] => F[Response[F]]. HttpRoutes[IO] is that function, with “no match” as an option so you can compose routes. The DSL pattern-matches method and path; the first matching case wins.3

http4s Service and DSL docs: you do not need a server to test a route. Construct a Request, run it, inspect status and body. .orNotFound turns “no case matched” into HTTP 404. 
import org.http4s.dsl.io.*
import org.http4s.implicits.*

val routes = HttpRoutes.of[IO] {
  case GET -> Root / "rates" / code =>
    rateOf(code) match
      case Some(n) => Ok(n.toString)
      case None    => NotFound()
  case _ -> Root / "rates" / _ =>
    MethodNotAllowed(Allow(GET))
}

val app = routes.orNotFound
val req = Request[IO](GET, uri"/rates/EUR")
app.run(req)   // IO[Response[IO]] — still a description

Ok("108") needs an entity encoder; strings are already in scope and come back as text/plain. JSON codecs are the next unit — do not add circe here. Ember (binding :8080) waits until integration testing: this unit’s edge is runRequest / tests / IOApp printing status lines, same rim rule as compile and unsafeRunSync.
