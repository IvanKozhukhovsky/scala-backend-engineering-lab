Why sentinels lie

The Scala 3 Book starts from a method that converts a string to an Int and returns 0 when conversion fails. That is the same shape of bug as a dummy user: callers cannot tell a real zero from a failed parse.1

Scala 3 Book, Functional Error Handling. The book’s first example is makeInt returning 0 on failure — then the same method returning Option[Int].

A missing row in a user table, a missing JSON field, and a missing query parameter are the backend versions of that problem. “Not here” is information. It belongs in the type, not in a comment and not in null.

Option, Some, and None

Scala’s replacement for null is the trio Option, Some, and None. Some and None are the two inhabitants of Option.2

Standard library, Scala 3.3.8: Option, Some, None.

Create values like this:

val present: Option[String] = Some("Ada")
val absent: Option[String]  = None

// Java interop: null becomes None, anything else becomes Some
Option("Ada")
Option[String](null)

Option.apply is the factory that turns a possibly-null JVM value into Some or None. Use it at the edge of Java APIs. Inside Scala code, write Some and None directly.3

Option.apply: “creates Some(x) if the argument is not null, and None if it is null.”

Optional fields are the same idea. An email address that a user may not have is Option[String], not null and not a blank string pretending to be “no email”. 

case class User(id: String, name: String, email: Option[String])

User("1", "Ada", Some("ada@example.com"))
User("2", "Grace", None)

Reading an Option

You already know match from Day 04, and map / filter / flatMap from Day 03. Option reuses both. The library’s own guidance is to treat an option as a collection of at most one element.4

From the Option Scaladoc: “The most idiomatic way to use an Option instance is to treat it as a collection or monad and use map, flatMap, filter, or foreach.”

Pattern match when both paths matter

def displayName(user: Option[User]): String =
  user match
    case Some(found) => found.name
    case None        => "guest"

Because Option is sealed, the compiler can warn if you forget None. That warning is the point of the type: absence is a case you must name.

map keeps absence intact

None.map(_.trim)                         // None
Some(" ada@example.com ").map(_.trim)    // Some("ada@example.com")

Mapping over None does not throw and does not invent a value. It stays None. That is the same “do the work only on the elements that exist” rule you used on List.

getOrElse is the fallback, get is not

findUser(users, "9").map(_.name).getOrElse("guest")

getOrElse returns the inner value or evaluates the default.5 Option.get instead throws NoSuchElementException on None. Do not call .get in this course. It reintroduces the crash that Option was meant to prevent.

getOrElse is equivalent to matching Some(x) => x and None => default. get is equivalent to throwing when the option is empty.

Combining two absences

A lookup can miss the user. A found user can still have no email. The Scala 3 Book’s second common style is a for / yield expression, which is flatMap written as a pipeline. If any step is None, the whole result is None. 

def primaryEmail(users: List[User], id: String): Option[String] =
  for
    user  <- findUser(users, id)
    email <- user.email
  yield email

You already used flatMap to flatten nested lists. Here the “list” has length 0 or 1, so flattening means “continue only if the value is present”.

What Option does not say

None means the value is absent. It does not say why. The Scala 3 Book is explicit that Try / Either exist for failures that carry a reason — a missing file, a downed database, a malformed payload.6 Those types are the next curriculum unit. Do not reach for them yet; do not pretend None is an error message.
