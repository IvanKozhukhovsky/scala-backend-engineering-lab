Try catches exceptions as values

The Scala 3 Book treats Try / Success / Failure as the same shape as Option / Some / None, with two extra facts: Try wraps code that can throw, and Failure still holds the exception.1

Scala 3 Book, Functional Error Handling, section Option isn’t the only solution. The longer Try walkthrough is in the previous edition of the same chapter. 
import scala.util.{Try, Success, Failure}

def parseInt(raw: String): Try[Int] =
  Try(raw.trim.toInt)

parseInt("7")    // Success(7)
parseInt("foo")  // Failure(NumberFormatException: ...)

Try(expr) evaluates expr and returns Success or Failure. It catches non-fatal exceptions only; serious JVM errors still abort.2 Consume it with match, the same way you consumed Option:

Try Scaladoc, Scala 3.3.8: “holds either a successfully computed value or the exception that was thrown.” Combinators catch non-fatal exceptions; get rethrows on Failure. 
parseInt(raw) match
  case Success(n)  => s"parsed $n"
  case Failure(ex) => s"failed: ${ex.getMessage}"

Do not call .get on a Try. On Failure it throws the original exception — the crash Try was meant to turn into a value.

Either carries a domain reason

Try’s failure type is always Throwable. A validation rule such as “port must be 1–65535” is not an exception; it is a domain message. Either is a disjoint union: exactly one of two types.3

Either Scaladoc, Scala 3.3.8: “Convention dictates that Left is used for failure and Right is used for success.” None is replaced by a Left that can contain useful information. 
def requirePositive(n: Int): Either[String, Int] =
  if n > 0 then Right(n)
  else Left(s"$n is not positive")

Right(21).map(_ * 2)          // Right(42)
Left("nope").map(_ * 2)       // Left("nope") — unchanged

Either is right-biased: map and flatMap transform Right and leave Left as-is. That is the same “work only on the happy path” rule you already used on Some. 

def parsePositive(raw: String): Either[String, Int] =
  parseInt(raw) match
    case Failure(ex) => Left(ex.getMessage)
    case Success(n)  => requirePositive(n)

A later unit will replace String on the left with a dedicated error type. For this lesson, a message is enough — the point is that the type still says “failure has a payload.”

Which container when

TypeUse when
Option[A] The value may be absent. There is no useful reason.
Try[A] Calling into code that can throw (parsing, files, JVM APIs).
Either[E, A] You want to name the failure yourself (validation, domain rules).

The Scala Book’s rule of thumb: Try when you need the exception; Option when you are avoiding null. Add Either when the reason is yours, not the JVM’s.4
