Schema migrations and transactions

Flyway first. Compose ConnectionIO. One transact is one rollback.

Lesson: Schema migrations and transactional boundaries. Docs: Flyway Java API, Quickstart - API, doobie FAQ. This repo pins OSS org.flywaydb:flyway-core:13.4.0 and flyway-database-postgresql:13.4.0. SQL lives at src/main/resources/db/migration (classpath:db/migration).

Flyway

Flyway.configure()
  .dataSource(url, user, password)
  .locations("classpath:db/migration")
  .load()          // not yet
  .migrate()       // applies pending V1, V2, … then records flyway_schema_history
  • Wrap migrate in IO { }. Construction does not JDBC.
  • Call it before repositories. A second call on the same catalog is a no-op.
  • Files: V1__Create_rate_table.sql (prefix V, separator __).

Transaction boundary

def bookRates(a: RateRow, b: RateRow): ConnectionIO[Unit] =
  for
    _ <- insertRate(a).run
    _ <- insertRate(b).run
  yield ()

bookRates(eur, gbp).transact(xa)     // both commit, or neither
insertRate(eur).run.transact(xa)     // committed
insertRate(eur).run.transact(xa)     // fails; EUR remains
  • FAQ: expose ConnectionIO so callers place one transact.
  • A single-row find may transact inside the repository.

Do

  • Share the JDBC URL between Flyway and the Transactor (H2: unique mem name, DB_CLOSE_DELAY=-1).
  • Keep rateOf as the pure Map lookup this unit.
  • Keep production postgresFlyway(...).load() unmigrated until a live Postgres exists (scala-024).

Do not

  • CREATE TABLE in Scala now that versioned SQL exists.
  • Transact each write when the pair must share a rollback.
  • Put Flyway or JDBC inside rateOf / convertAmount.
  • Introduce Testcontainers, Flyway clean, undo, Java migrations, or custom Strategy in this unit — Testcontainers is scala-024.
