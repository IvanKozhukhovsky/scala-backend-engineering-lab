IO and referential transparency

An IO is a description of an effect. Constructing it does not run the body.

Lesson: Cats Effect IO and referential transparency. Docs: Getting Started, IO, IO API. This repo pins cats-effect 3.6.4.

Description

def lookupRate(code: String): IO[Option[Int]] =
  IO(rateOf(code))
  • An IO[A] is a pure value that describes a computation producing A.
  • IO.apply / IO { } suspends a by-name body. Construction does not execute it.
  • IO.pure(x) lifts an already-known value (by value). Do not put side effects in pure.

Referential transparency

val tick = IO.println("hey")
for
  _ <- tick
  _ <- tick
yield ()
  • Naming an IO and sequencing it twice runs the effect twice (not memoized).
  • Future is eager and memoized: sharing one started future does not re-run the body.
  • Laziness is what makes that rewrite safe for effect descriptions.

map, then run at the edge

lookupRate(code).map(maybe => maybe.map(_ * amount))

object App extends IOApp.Simple:
  val run = convert("EUR", 10).flatMap(IO.println)

// tests / REPL only:
import cats.effect.unsafe.implicits.global
convert("EUR", 10).unsafeRunSync()
  • map transforms the successful result inside the description.
  • Apps: IOApp.Simple and a val run.
  • Tests/REPL: unsafeRunSync with unsafe.implicits.global. Not inside library functions.

Do

  • Keep the domain lookup as a pure Option / Either function. Wrap it in IO(...).
  • Return IO[...] from library code; execute only at the rim.

Do not

  • Treat an IO like a Future: construction is not a start.
  • Call unsafeRunSync (or Await) inside lookupRate / map.
  • Put effects inside IO.pure.
  • Introduce fibers, Resource, cancelation, or FS2 — those are later units.

Eager predecessor: Futures and ExecutionContext. Purity at function scale: Purity and functional core.
