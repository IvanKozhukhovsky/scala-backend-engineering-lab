Futures and ExecutionContext

A Future is a placeholder for a value that will exist later. Constructing it starts the work.

Lesson: Futures, execution contexts and concurrency fundamentals. Docs: Futures and Promises, Future.apply, ExecutionContext, Await.

Placeholder

def fetchRate(code: String)(using ExecutionContext): Future[Option[Int]] =
  Future {
    rateOf(code)
  }
  • A Future[T] holds a T that may not be ready yet, or an exception.
  • Future.apply starts the body on an ExecutionContext and returns immediately.
  • Future.successful(x) is already done. It does not schedule work.

ExecutionContext

  • Think of it as a thread pool: it decides where the body and later maps run.
  • Library methods take (using ExecutionContext). Do not import Implicits.global inside them.
  • Tests and @main import ExecutionContext.Implicits.global at the edge.

map, then maybe Await

fetchRate(code).map(maybe => maybe.map(_ * amount))

import ExecutionContext.Implicits.global
Await.result(fetchConverted("EUR", 10), 1.second)
  • map transforms a successful value. A failed future stays failed. Needs an ExecutionContext.
  • Await.result blocks the current thread until the value or the timeout. Tests and mains, not the core, not inside map.
  • MUnit may instead return the Future from the test body and wait for you.

Do

  • Keep the domain lookup as a pure Option / Either function. Wrap it in Future { }.
  • Create two futures before combining them if you want the work to overlap.

Do not

  • Treat a Future as a lazy recipe. The body starts at construction.
  • Call Await or Thread.sleep inside the fetch functions.
  • Introduce an IO type — that is scala-014.
  • Write a Promise, a custom pool, or blocking { } in this unit.
