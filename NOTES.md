# Teaching Notes

- Prefer a short title plus one observable outcome before expanding a lesson or a next-unit report.
- Do not skip curriculum units merely because later code appears to use the concept.
- Prefer retrieval questions before re-explaining material that was already covered.
- For an exercise, request or inspect the learner's attempt before offering a complete implementation.
- Give the smallest useful hint first. Escalate to a full explanation only when needed or explicitly requested.
- A file existing is evidence of an attempt, not proof of mastery.
- Verification should use objective evidence where possible: tests, compiler output, a code review, or an explanation by the learner.
- Before marking a unit verified, run `scala-cli fmt --check` as well as focused tests. If formatting fails, do not rewrite the learner file; hint them to run `scala-cli fmt` on it (or align the `=>` in the reported match).
- MUnit is pinned at `1.0.4`. `munit-scalacheck` has no `1.0.4`; the 1.0-line pin is `1.0.0`.
- `scala-011` teaches purity at function scale: core returns values, shell does I/O. Do not introduce `IO` / Cats Effect (`scala-014`).
- `scala-012` teaches packages as namespaces and import arrows: shell → core only. The exercise lives in `day12.core` / `day12.shell`, not a single `ExercisesDay12.scala`. Not an sbt/mill subproject. A named capability, if introduced later, is declared in the core package; prefer passing values as in `scala-011`.
- The learner mixed value flow (core → shell) with the import arrow (shell → core). Retrieval should ask which *file* writes `import`, not only which way data moves.
- `scala-013` teaches `Future` as eager stdlib asynchrony: `Future.apply` starts the body. Pass `using ExecutionContext`; import `Implicits.global` only in tests/`@main`. `Await.result` is the test/main edge, not the fetch. Keep `unitPrice` / `rateOf` as a pure `Option` function. Do not introduce `IO` (`scala-014`), `Promise`, custom pools, or `blocking { }`. Prefer `Future { }` over `Future.successful` for the scheduled lookup. The learner used `Future.successful(None)` to skip the lookup when `qty < 1`; they described the `map` path as unpacking `Option` after the Future resolves. If they say a function "gets" the ExecutionContext, ask whether it *schedules* work or only has `using` in scope.
- `scala-014` teaches `IO` as a lazy description: `IO.apply` / `IO { }` does not run at construction; `IO.pure` is by-value (no side effects inside). Contrast with eager memoized `Future`. `map` stays inside the description; run at the edge with `IOApp.Simple` or test/REPL `unsafeRunSync` + `cats.effect.unsafe.implicits.global`. Keep `rateOf` / `unitPrice` pure. Do not introduce fibers, `Resource`, cancelation, FS2, or `munit-cats-effect` yet. Repo pin: `cats-effect` `3.6.4`. The learner used `IO.pure(None)` for `qty < 1` and described construction as "description in memory" until `unsafeRunSync`. If they say an `IO` "runs when you map," ask when the *body* of `IO { }` executes.
- `scala-015` teaches `Resource.make` / `use` (release on success, error, cancel), cooperative `fiber.cancel`, and `background` over bare `start`. Keep tests on `unsafeRunSync` / `FunSuite` — no `munit-cats-effect` yet. Do not introduce `Ref` / `Deferred` / `Semaphore`, `uncancelable` masking, or FS2 (`scala-016`). If they `start` without joining/canceling, ask who owns the fiber's lifetime. If they use the handle after `use`, ask when release ran.
- `scala-016` teaches `Stream[F, A]` as a lazy pipeline: `emit` / `emits`, pure `map` / `filter` / `take`, effectful `evalMap` / `evalTap`, and `compile.toList` / `drain` / `fold` at the edge. Keep `rateOf` pure; suspend in `IO(...)` inside `evalMap`. Do not introduce file/socket I/O, `through` pipes, `parJoin`, Kafka, or `bracket` on streams yet. Repo pin: `fs2-core` `3.12.2`. If they call `unsafeRunSync` inside `evalMap`, ask where compile belongs. If they materialize a whole `List` before streaming, ask what pull-based buys you.
- `scala-017` teaches HTTP as a contract: URI identifies the resource, method is the operation, status is the outcome. `GET` is safe; `PUT`/`DELETE` idempotent; `POST` is neither (RFC 9110). http4s `HttpRoutes.of` + `orNotFound`; run a constructed `Request` — no Ember, no JSON. 404 = missing resource; 405 = wrong method (send `Allow`). Keep `rateOf` pure; HTTP only chooses the status. Repo pin: `http4s-dsl` `0.23.36`. The learner treats `/quotes/:code` as a GET-only URI template: `POST /quotes/JPY` is 405 without `rateOf`; GET miss is 404. If they say 404 means “method is allowed,” ask what 404 answers (existence) vs what 405 answers (operation). If they bind a port to test, ask what `HttpRoutes` already is.
- `scala-018` teaches JSON as a representation at the rim: circe `Encoder`/`Decoder` (Scala 3 `derives Codec.AsObject`), http4s `jsonOf` / `jsonEncoderOf`. Prefer `attemptAs.value` (Either) over `req.as` — without Ember a `MessageFailure` fails the `IO`. 400 = malformed JSON; 422 `UnprocessableContent` = well-formed JSON the resource cannot process (`invalid_json`, domain `Either`). GET miss stays 404 `not_found`; POST unknown code in the body is 422, not 404. Distinct `{"error":…}` strings; do not collapse 404/405/422. Keep `rateOf` / `convertAmount` / `orderOf` pure. Repo pin: `http4s-circe` `0.23.36`. No Ember, no `CirceEntityCodec` as a global import, no `Validated`. The learner mapped POST `UnknownCode` after a non-exhaustive match warning; they described GET `/orders/JPY` as a path miss and POST JPY as a body field on a known URI, and 422 vs 400 as “JSON structure is correct.” If they say 404 means “we know this URI,” ask whether the *item* exists at that path. If they map missing qty and `{not json` to the same status, ask which failure is syntax.
- `scala-019` teaches wiring: load Ciris `ConfigValue` once (`env`/`prop`/`or`/`as`/`default`/`secret`/`parMapN`/`load[IO]`), pass `minQty: Int` into a pure `convertAmount`, pass `StructuredLogger[IO]` into routes. `Secret.toString` is a SHA-1 prefix; never log `.value` or put it in JSON. Tests: inject `QuoteConfig`, `StructuredTestingLogger` / `NoOpLogger`. Repo pins: `ciris` `3.15.0`, `log4cats-core` `2.7.1`. No Ember, slf4j/logback, http4s `Logger` middleware, metrics, or tracing (`scala-028`). If they `sys.env` inside `orderOf`, ask what the test would have to own. If they interpolate `s"code=$code"` as the only record, ask where `ctx.get("code")` would read. The learner said `orderOf` with `sys.env` would own the configuration dependency; as written it only owns the domain rule and a prepared `Int`.
- `scala-020` teaches Ember over loopback: `EmberServerBuilder` + `EmberClientBuilder` as `Resource`, bind `127.0.0.1` and `port"0"`, send absolute `Server.baseUri`, `expect` is 2xx-only (`UnexpectedStatus` on 404/422), 4xx bodies via `Client.run.use`. `Client.fromHttpApp` is still in-process — not the integration test. Keep in-process `HttpApp.run` for the fast contract suite. Inject `DeskConfig` values; do not load env in the live test. Repo pins: `http4s-ember-server` / `http4s-ember-client` `0.23.36`. No slf4j/logback (NOP lines in tests are expected), no `Logger` middleware, no `munit-cats-effect`, no `Router`, no DB. If they `expect` a 404, ask whether they wanted a status or a decoded `ApiError`. If they bind `0.0.0.0` and use `baseUri`, ask whether that host is a destination. If they use `fromHttpApp`, ask which layer adds `Date`.
- `scala-021` teaches relational modeling plus doobie `sql` interpolator as a `PreparedStatement`: `$code` becomes `?`, inspected via `Query0.sql` / `Update0.sql` with no database. `query[CaseClass]` is SELECT-list order, not column names. `ConnectionIO` is a description; `Transactor` / `doobie-postgres` / Hikari / H2 wait for `scala-022`. Keep `rateOf` as `Map.get`. Pin: `org.typelevel` `doobie-core` `1.0.0-RC13`, package `org.typelevel.doobie` (not `org.tpolecat` / `doobie.`). Do not quote `$code` (`'?'` is a literal). If they `s-interpolate` the code, ask whether the hostile string is syntax or a bind. If they `transact`, ask what `findRate("EUR").sql` already is. The learner said `GBP` is not in the SQL; it is a parameter sent separately so injection cannot change the statement.
- `scala-022` teaches the repository as the JDBC rim: inject `Transactor[IO]`, `query.option.transact(xa)` / `update.run.transact(xa)`, keep `rateOf` as `Map.get`. Production shape: `doobie-postgres` + `HikariTransactor.fromHikariConfig` (`Resource`; `org.postgresql.Driver`). Tests: `Transactor.fromDriverManager` + `doobie-h2` + `jdbc:h2:mem:$name;DB_CLOSE_DELAY=-1` (unique name). Pins: `doobie-postgres` / `doobie-hikari` / `doobie-h2` `1.0.0-RC13`. Do not call `postgresPool.use` (no live Postgres). Do not put `transact` inside `rateOf`. Do not use `.unique` for a miss. Do not introduce Flyway (`scala-023`), Testcontainers (`scala-024`), `H2Transactor`, `pgtypes`, `LISTEN`, or custom `Strategy`. If they forget `DB_CLOSE_DELAY=-1`, ask when `transact` closes the connection. If they `sys.env` the JDBC URL inside `find`, ask what the test would have to own. If they `.unique` a missing fill, ask what `.option` already is. The learner said `DB_CLOSE_DELAY=-1` keeps the same mem database after the first operation; the precise mechanism is that `transact` always closes the connection and H2 mem dies with the last one. Unique `name` still isolates tests.
- `scala-023` teaches Flyway as the schema owner and `ConnectionIO` composition as the transaction boundary. Pin: OSS `flyway-core` / `flyway-database-postgresql` `13.4.0` (Java API page, 26 Aug 2026). SQL: `V1__…sql` / `V2__…sql` under `src/main/resources/db/migration`; `//> using resourceDir "./src/main/resources"`; API default `classpath:db/migration`. Wrap `migrate()` in `IO { }` — `configure`/`load` do not migrate. Call migrate before repositories. Idempotent: second call returns `migrationsExecuted = 0`. Compose two inserts in `ConnectionIO`, one `transact`; two `transact`s leave the first row if the second hits the PK. FAQ: expose `ConnectionIO` so callers place the boundary. Keep `rateOf` as `Map.get`. Tests still H2 mem + `DB_CLOSE_DELAY=-1` (unique name); share that URL with Flyway. Do not `CREATE TABLE` in Scala. Do not transact inside `bookFills`. Do not `postgresFlyway.migrate` (no live Postgres). Do not introduce Testcontainers (`scala-024`), Flyway `clean` / undo / Java migrations, `withoutTransaction`, or custom `Strategy`. Flyway 13.4.0 warns that H2 `2.4.240` (from `doobie-h2`) is newer than its verified `2.3.232`; keep the doobie pin. If they `CREATE TABLE` in `migrateDesk`, ask where `flyway_schema_history` would come from. If they transact each `insertFill`, ask whether the duplicate-PK test should still see `EUR`. If they call `migrate()` outside `IO`, ask when JDBC first runs. The learner first answered the one-`transact` rollback, then named the split: the first `transact` has already committed before the second starts, so a PK failure rolls back only the second insert and `findFill("EUR")` still sees the row.
- `scala-024` teaches a live Postgres via Testcontainers: construct `PostgreSQLContainer` does not start Docker; `start()` pulls/runs/waits; `stop()` is release. Wrap in `Resource.make` (MUnit — no JUnit `@Container`). Pin: Java `org.testcontainers:testcontainers-postgresql` `2.0.5`; package `org.testcontainers.postgresql`; image `postgres:16-alpine`. Read `getJdbcUrl` / `getUsername` / `getPassword` (`jdbc:postgresql://` + `getHost()` + mapped port). Flyway then `Transactor.fromDriverManager` + `org.postgresql.Driver`; credentials are container `test`/`test`, not H2 `sa`. `select version()` contains `PostgreSQL`. Keep the H2 suites. Do not use `jdbc:tc:` (hidden start; default stop-on-last-close fights `transact`). Do not hard-code `localhost:5432`. Do not alias `quotesPg`. Do not put Docker/JDBC in `rateOf`. Do not introduce JUnit 5, `testcontainers-scala`, Flyway `clean`, or reusable containers. App Dockerfiles (`scala-025`) are a different image. If they point at `localhost:5432`, ask whose laptop owns Postgres. If they use `jdbc:tc:`, ask when `transact` closes the connection. If they skip `stop` on a failed assertion, ask what Day 15 already does with `Resource.use`. The learner first mixed `Resource.make` with transaction success/failure, then named the split: after a `transact` inside `use`, Postgres is still running; `pg.stop()` runs when `use` ends.
- `scala-025` teaches the *app* image as a different artifact from Day 24’s `postgres:16-alpine`. Image = immutable package; container = isolated process; Dockerfile = recipe. Pin `eclipse-temurin:21-jre-alpine-3.24` (JVM 21, JRE, Alpine 3.24 — not `latest`, not a JDK, not Postgres). `WORKDIR /app`, `COPY quotes.jar`, `ENV QUOTES_CODE=EUR`, exec-form `CMD ["java", "-jar", "quotes.jar"]`. Ciris still loads `env` at the rim; `rateOf` stays `Map.get`. Host build: `scala-cli --power package . --assembly --preamble=false -o packaging/quotes/quotes.jar --main-class day25.Day25` then `docker build -t quotes:0.1.0`. Tests inspect `dockerfileOf` / the checked-in file — they do not `docker build` (CI already runs Testcontainers). Whole-repo assembly still contains Testcontainers (compile dep); do not pretend the image is slim. Do not `COPY . .`, bake tokens, `FROM postgres`, or install Scala CLI in the runtime. Do not introduce Compose, `jlink`, GraalVM, `USER`, health checks, or CI publishing. Exercise: `deskRuntime` + `packaging/desk/Dockerfile` matching `dockerfileOf` (`desk.jar`, `DESK_CODE=GBP`). If they `FROM postgres`, ask which process is PID 1. If they `COPY . .`, ask whether tests and Scala CLI belong in the runtime. If they `ENV` a token, ask what `docker history` would show. The learner named exec-form `java` as PID 1 and that Postgres is not started. They first called `GBP` a program argument, then described `--env` as an override. Ciris reads process env: Dockerfile `ENV` is the default; `docker run --env DESK_CODE=EUR` is what that container sees. `CMD` argv is `java`, `-jar`, `desk.jar`.
